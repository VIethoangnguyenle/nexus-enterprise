## High

**H1. The ⋯ button takes up layout space in every navigator row on touch devices. This is the cause of the uneven "Nhóm" spacing the coordinator saw.** `components/spaces/ChatNavigator.tsx:201-211`
- The row-menu `IconButton` uses the `absolute` utility on the `<button>` itself.
- `index.css:719-721` contains an **unlayered** rule, `@media (pointer: coarse) { :where(button, …) { position: relative } }`. Tailwind 4 utilities live in `@layer utilities`, and an unlayered declaration beats a layered one whatever the specificity. On any coarse-pointer device the button becomes `position: relative` and drops into normal flow under the 36px link.
- Result: each `<li>` is 36 + 28 = 64px, which gives the 66px pitch seen in `phase-10-screens/1440-light-4-toast.png` and `-5-restored.png`.
- The screenshot script creates its context with `hasTouch: true` (`scratchpad/p10-shots.mjs:27`), so the bug shows at 1440 there. Real users hit it on any touch laptop or tablet.
- The button is `opacity-0`, so the gap looks empty. "Đối soát giao dịch" looks hugged to the header only because every row's gap sits *below* its link.
- `ConversationStream.tsx:403` already documents this trap and works around it.
- Fix: put the absolute positioning on a wrapper and leave the button in flow inside it:
  ```tsx
  <div className="absolute right-1.5 top-1/2 -translate-y-1/2 opacity-0 group-hover:opacity-100 group-focus-within:opacity-100">
    <IconButton size="sm" … />
  </div>
  ```
- Add a test assertion, or a Playwright check under `hasTouch`, that each row's height equals the link's height.

**H2. The ⋯ row menu cannot be reached on touch-only wide screens.** `ChatNavigator.tsx:207-208`
- The menu only appears on `group-hover`, `group-focus-within` or `focus-visible`. A tap on a tablet in landscape (≥ md) never hovers, and tapping the row navigates away.
- There is no long-press fallback on the navigator rows. Dragging is HTML5 DnD, which does not work on touch.
- So a tablet user has no way to put a conversation into a section, or take it out, from the desktop navigator.
- Fix: use `pointer-coarse:opacity-100` on the wrapper, or add the `useLongPress` that `MessageBlock` uses.

**H3. Deleting a reply subtracts it from the root's reply count twice.** `hooks/useMessageLifecycle.ts:58`
- `onSuccess` computes `replyCount = rootOf(channelId, parent).reply_count - 1` from the **current** cache.
- The server also sends the `message_deleted` frame to the deleter (spec: "the channel's viewers receive"). The frame carries the server's count and is applied by `applyMessageDeleted`.
- If the frame lands before the HTTP response, the cache already holds N-1 and `onSuccess` writes N-2. The frame is broadcast from inside the request, so this is the likely order.
- With N=1 → 0 → `withReplyCount(…, 0)` (`chat-cache.ts:146`), the thread summary is wiped. A root that still has replies shows "no replies" until the next refetch.
- The doc comment "Applying it twice changes nothing" (`chat-cache.ts`) is true for removing the reply but false for this count.
- Fix options:
  - Do not touch `reply_count` in `onSuccess`: remove the reply and invalidate `messages(channelId)`.
  - Or make the DELETE response carry `reply_count`, `keep_placeholder` and the parent, and apply exactly the frame's payload.
- Add a test: frame first, then `onSuccess`, and assert the count is N-1.

## Medium

**M1. The placeholder decision uses a possibly stale reply count.** `useMessageLifecycle.ts:57`
- `keepPlaceholder: (message.reply_count ?? 0) > 0` reads the message object captured when the menu opened.
- If someone replies after that (or the count is stale), the client removes the root from the stream while the server keeps a placeholder. The later frame's `mapMessage(…tombstone)` then finds nothing to patch, and the thread with its replies disappears from the stream until a refetch.
- Same fix as H3: trust the server's answer or frame, or invalidate after success.

**M2. Editing an old markdown message turns its formatting into literal characters.** `lib/message-model.ts:86-89`, used by `useMessageActions.ts:64`
- `toEditorHtml` escapes non-HTML content into `<p>` lines.
- `MessageContent.tsx:19-30` still renders that content as **markdown**. A pre-rich-text message `**Hạn chót** thứ 6` shows bold, but opens in the editor as literal `**Hạn chót**`.
- Changing any character and saving stores `<p>**Hạn chót** …</p>` as HTML: the formatting is lost and the asterisks show for everyone.
- Fix: convert markdown to HTML before loading it into the editor (render it with the same markdown pipeline, then sanitise). Or offer edit only on `content_format === 'html'`.

**M3. The edit editors do not send mentions.** `MessageEditBox.tsx:52`, `ChatEditor.tsx` (`handleSend` edit branch), `api/messaging.ts` `EditMessageInput`
- The editor does include the `Mention` node, so a person can @-pick someone while editing.
- `onSave(html, empty)` never passes `mentionsOf(editor)`, and `EditMessageInput` has no `mentions` field.
- The `span[data-mention]` is stored, but the person added in the edit is not notified, and `applyMessageEdited` keeps the old `mentions`.
- The spec does not say either way. Decide (notify or not) and record it in `docs/specs/chat-message-lifecycle`, or remove the mention picker from edit mode.

**M4. On phones, the composer can stay stuck in edit mode for a message that was deleted.** `useMessageActions.ts:62-69`
- If the message being edited is deleted elsewhere (frame), `editing` still holds it.
- On save, the server answers 404 and `onError` puts `setEditing({message, draft})` back. The phone composer then shows "Đang sửa tin" again for a message that is no longer in the stream.
- The user can only get out with Huỷ. The same thing happens if the frame arrives before the user presses Lưu.
- Fix: clear `editing` (and `deleting`) when a `message_deleted` for that id is applied, or when the message is no longer in the list. On a 404, show a toast and close instead of reopening.

## Low

- **L1.** `useEditMessage.onMutate` (`useMessageLifecycle.ts:23`) does not `cancelQueries` before the optimistic patch. A refetch already in flight (focus, or the `markUnread` invalidation) can briefly bring back the old text. `onSuccess` fixes it afterwards, so the only effect is a flicker.
- **L2.** `useMarkUnread` (`useMessageLifecycle.ts:68-72`) invalidates `messages(channelId)` but not `thread(parentId)`. When a reply is marked unread, the open thread panel's root (taken from the thread cache, `ThreadPanel.tsx:72`) keeps `thread_unread_count: 0`. The next thread refetch then triggers the auto mark-read effect (`ThreadPanel.tsx:100-102`) and silently undoes the action, after the toast has already said "Đã đánh dấu chưa đọc". Decide whether an open thread should re-read on refetch.
- **L3.** `ChatNavigator.tsx:176`: the drag payload is the title, not the id. That is correct per the no-ID rule; noted as verified.

## Verified non-issues

- Section `channel_ids` are never `null`: the backend normalises them (`rest/sections.go:23`), and the list query does the same with `?? []`.
- The `/chat-sections` routes are present in the `vite.config.js` re-dispatch regex (line 40). `/api/messages/:id/unread` falls under the flat `/api/messages` entry.

- The deletion system line renders the server's text, which per the spec contains names, not IDs (`ConversationStream.tsx:464-470`).
