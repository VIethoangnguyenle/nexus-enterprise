Realtime: `websocket.store` now remembers the last actor per request (`approvalActivity`, 2 small edits in a shared file) so a row can be attributed.

**Motion** (DESIGN.md §7, via `lib/motion`): panel and dialog enter/exit through `SidePanel`/`Dialog`; first batch of rows staggers (30 ms, max 8, none under reduced motion); rows entering/leaving use `m.row`; tab content `m.route`; realtime wash `rt-wash` + `rt-tag` in the actor's hue 2.4 s ("Đức vừa duyệt"), burst line from 3 changes; own changes and unattributable ones are not washed; reduced motion keeps the wash, moves nothing. `grep -E "transition-all|duration-[0-9]|animate-bounce|z-\[|rgba\(" src/components/approval src/routes/_workspace/approval*` is empty (also no `animate-pulse`, hex, raw palette).

**Backend (approval REST, additive)** — see "REST contract mismatches" for why:
- Display names beside ids: `created_by_name`, `department_name` (request), `user_name` (assignment), `actor_name` (audit), `approver_name` (step), `created_by_name` (template). `rest/names.go` + `store.DisplayNames` (users.display_name → username; UA node → role name; department id / UA id → department name; unknown keys omitted, never an id). One lookup per response; a failed lookup is logged and the response goes out without names.
- New `GET /api/approval/requests/:id` → request + steps and form fields from the frozen snapshot + every assignment; same visibility paths as the audit trail (requester / any assignee / department scope), 403 otherwise. Under the existing `/api/approval` entry of `vite.config.js`, so no proxy change was needed (checked, not edited).
- `POST /requests` accepts `template_id`; `entity_id` optional (server generates).
- `UpdateTemplate` now persists steps and conditions (it silently did not), in one transaction; an empty `form_fields` list clears them, an absent one keeps them.
- `form_data_json` added to the my-requests and department queries (rows show the amount).
- `GetTemplate` of an unknown id is `ErrNotFound` (was a 500).
No schema change, no new table, per-tenant schemas untouched (`DisplayNames` runs on the shared schema where users/roles/departments live).

**Spec:** new `docs/specs/approval-screens/spec.md` (indexed in `docs/specs/README.md`), with its known gaps under `## Status`.

## REST contract mismatches found (client vs `rest/handler.go`)
1. **Edit switched templates off.** `PUT /templates/:id` writes `is_active` and `priority` from the body as given; the client omitted both, so every edit set `is_active=false`, `priority=0`. Client type now requires both; builder sends the template's own values (tested).
2. **Server ignored steps on update** (store wrote name/flag/priority/form_fields only). The builder showed a chain the DB never got. Fixed in `store.UpdateTemplate` (integration test red→green).
3. **Create request ignored the chosen template.** Body had no `template_id`; the server re-matched by `entity_type` + conditions (client sent no `entity_fields`), so two templates of one type could yield another template than the one whose form was filled. Now `template_id`.
4. **Invented `entity_id`** (`crypto.randomUUID()`), required only because the server insisted on one.
5. **`creator_manager` approver type** offered by the old UI; `assignStep` rejects it ("unknown approver_type"). Dropped from the builder. A saved template of that kind opens with an empty approver, forcing a real choice.
6. **My-requests / department rows had no `form_data_json`** so no amount could show.
7. **Pending/history rows carried only the viewer's assignment**, so the old "Step 2/1" counted assignments; the chain needs all of them (detail endpoint).
8. Approve / reject / batch bodies, history paging params, `active_only`: match their structs (pinned in `api/approval.test.ts`).

## Decisions where the mockup was silent
1. Tab names: mockup has "Chờ tôi duyệt / Tôi đã gửi / Tất cả"; the task also asks for history and department, so five tabs: Đã xử lý (history), Phòng ban (department), Mẫu (templates).

3. Template builder = in-place screen (`?edit=`), not a dialog: 520 px is too small for fields + steps. Step cards, ↑/↓ reorder, remove (never the last).
4. Approver kinds: Một người / Vai trò / Phòng ban (the three the server resolves), segmented control + picker; people via `PeoplePicker` (max 1), role/department via new `primitives/ChoicePicker` (same combobox rules, Esc closes only the list).
5. New primitive `Checkbox` (eslint forbids raw `<input>` outside primitives and none existed).
6. No comment box on Duyệt (mockup has none); reject reason is the dialog.
7. "Hoàn tác" after Trả lại is **not offered**: there is no un-reject endpoint (a rejected request is final). Dialog copy says the sender "có thể gửi một đề nghị mới" instead of the mockup's "gửi lại".
8. Narrow table: sender + amount under the title (mockup mobile), "Gửi time" on wide rows only.
9. Mobile: the sheet's actions get `max-md:pb-18` because the legacy `MobileNav` (z-[9999], not mine) floats over the sheet's bottom edge and hid Duyệt / Trả lại (found by the screenshot run).
10. Status words: "Chờ bạn" (my pending assignment on the current step), "Chờ <tên bước>", "Đã duyệt", "Trả lại" (mockup's word for reject), "Đã huỷ"; chain: "Đang chờ", "Chưa tới", "Bỏ qua", "Hết quyền duyệt".
11. Trail shows all server actions including `assigned` ("được giao duyệt") and system entries ("Chuyển sang bước tiếp theo").

## Open questions / concerns
1. **Role/department approvers are weak on the server.** `assignStep` creates one assignment whose `user_node_id` is the role/department node, and `Approve` looks the assignment up by the caller's user node, so nobody can act on it; `role_in_dept` also assigns to "scopes" it resolves. The builder offers them (task asked for pickers by person/role/department; the server accepts them) but only "Một người" is end-to-end usable today. Needs a backend decision (expand to members at assignment time).
2. **Department picker value.** `GET /departments` returns the department row id; the department UA is `ngac_ua_id` (not exposed). Names resolve for both, but which one `assignStep` should receive is undecided.
3. **No undo / withdraw / resubmit** for a rejected request (and no cancel endpoint, so the mockup's "Vinh rút đề nghị" scenario cannot happen).
4. **Department tab scope.** Requests made from the UI carry scope/department `default` (the form has neither), so they show to requester + approvers + whoever can read the `default` scope. A real scope needs the workspace's OA, which the client does not have.
5. **Sidebar count pill** (mockup nav "Phê duyệt 2") not added: `AppSidebar` is outside this change. The tab carries the count; a `useApprovalPending().data.total` read is all it needs.
6. **`websocket.store.ts` and `primitives/index.ts`** were edited outside the approval folders (approvalActivity: 2 additive blocks; exports of `Checkbox`, `ChoicePicker`). Another group editing the same lines would merge-conflict trivially.
7. **`MobileNav` z-[9999]** floats over every full-screen sheet (drive too); the approval workaround is padding. The shell/mobile redesign should put the sheet above or the nav under it.
8. Stranger on `GET /requests/:id` or audit returns 500 when the policy service is down (fails closed, intended) and 403 when up; not re-verified with policy running here.
9. `AlertBanner` (legacy tokens) is still used inside the create dialog for failures; `Select`/`Textarea` are the legacy primitives with aliased tokens (shorter than `TextField`: 36 vs 40 px).
10. Plan/phase files not updated (04b-approval, 06 group 4 can be ticked by whoever owns them).
