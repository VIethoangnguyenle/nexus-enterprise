# Red-team: Assumption Destroyer + Scope Auditor — plan 261017-1645-authz-overprivilege-fixes

Reviewed: plan.md, phase-01..08. Verified against code + dev DB (`nexus-enterprise-postgres-1`, 5433) on 2026-10-17.

## Finding 1: The refresh membership check runs after the token is spent, so the "503, keep the session" path still logs people out
- **Severity:** Critical
- **Location:** Phase 04, Requirements item 4 ("after `Rotate` … Policy/DB error → `ErrUnavailable` mapped to 503 without revoking")
- **Flaw:** `Rotate` marks the presented refresh token spent and mints its successor before returning. If `requireActiveMember` then fails with a policy or DB error, the handler returns 503 and never sets the new cookie. The browser still holds the spent token. Its next refresh is treated as a replay, which revokes the whole session family. Separately, the frontend logs the user out on that 503: `withRefreshRetry` gets `null` from the refresh, hands back the original 401, and `toResult` calls `logout()` on that 401.
- **Failure scenario:** A 30 s policy blip during the morning token expiry. Every tab that refreshes gets a 503, the UI logs out (client.ts), and the next refresh attempt trips replay detection and revokes the session on the server (refresh.go:161-165). That is the "outage logs everybody out" case that the plan's risk table says this design mitigates.
- **Evidence:** `backend/services/auth/internal/domain/refresh.go:161-176` (replay → revoke; `rec.Spent = true` set before mint), `refresh.go:202` (RefreshSession calls Rotate first), `backend/services/auth/internal/rest/session.go:111-118` (clears cookie on any error), `frontend/src/api/client.ts:156-162` and `:165-168` (401 after a failed refresh → `logout()`).
- **Suggested fix:** Check membership before spending the token: `Lookup` (exists, refresh.go) → `requireActiveMember` → `Rotate`. On 503, do not touch the cookie. In the frontend, `withRefreshRetry` must tell "refresh unavailable" apart from "session over" and must not turn a refresh 5xx into a logout. Add the test: policy down → 503, then the same cookie still refreshes once policy is back.

## Finding 2: Joining "graph first" breaks every OTP signup and every org workspace that has no TenantMember UA
- **Severity:** Critical
- **Location:** Phase 07, Requirements "Writers, graph first" (`joinTenant` calls strict `assignTenantNGAC` before insert) and Risk row "switch [autoProvisionWorkspace] to `joinTenant`"
- **Flaw:** `assignTenantNGAC` returns an error when `TenantMember_<ws>` does not exist. That UA is created only by `initTenantNGAC`, and only `provisionTenant` calls that. `autoProvisionWorkspace` (the OTP signup path) never creates it. In the dev DB, **83 of 83 personal and 8 of 27 org workspaces have no TenantMember UA**. The plan also says sign-in callers stay lenient, but `joinTenantByDomain`'s caller returns the error and fails the sign-in.
- **Failure scenario:** (a) New OTP signup: assign fails, so no `tenant_users` row is written. `ListTenantsByUser` is empty, and the Phase 04 `requireActiveMember` returns 401 on every refresh. (b) A Google `hd` user of one of the 8 org workspaces: the error goes through `google.go:84-86` and sign-in fails outright. (c) The plan's success criterion "no code path writes tenant_users active before the graph edge" is already false in the strict `provisionTenant` branch (insert, then assign), and the plan does not list that branch.
- **Evidence:** `backend/services/auth/internal/domain/provisioning.go:28-49` (no initTenantNGAC), `:209-216` (error when the UA is missing), `otp.go:300`, `tenants.go:96-101` (strict branch inserts before assigning), `tenants.go:132-139`, `google.go:84-86`. Dev DB query: workspaces lacking `TenantMember_<id>`: personal 83, organization 8.
- **Suggested fix:** Membership is "under `<ws>_Members`", so grant it there: for a member, assign directly under `MembersUAName` (or under Owners for the owner), and treat TenantMember as optional. Otherwise, make `initTenantNGAC` idempotently backfill the missing UAs, both in a migration before 060 and in `autoProvisionWorkspace`. Keep the domain join lenient by logging and returning a nil tenant. Add `tenants.go:96-101` to the Phase 07 file list.

## Finding 3: Closing sockets does not cut a removed member off, because the client reconnects and WS auth checks only the JWT
- **Severity:** High
- **Location:** Phase 04, Requirements item 6 and item 4 ("Exposure … 0 for … live sockets")
- **Flaw:** WS authentication checks only the JWT signature and takes `tenantID` from the claims. There is no membership check. The frontend reconnects on any close code other than 1000. The removed member's access token stays valid for up to 15 min, so the socket comes straight back. It rejoins tenant presence (`broadcastToTenant`) and can subscribe to the workspace stream again.
- **Failure scenario:** An admin removes X. The hub closes X's socket, the browser reconnects within the backoff window, and X sees tenant presence and live events again for up to 15 min. The test "removal event closes sockets" passes while the exposure the plan calls 0 is still there.
- **Evidence:** `backend/services/messaging/internal/grpc/hub_conn.go:99-116` (ParseWithClaims, `c.tenantID = claims.TenantID`), `frontend/src/stores/websocket.store.ts:282` (only code 1000 stops reconnect), `hub_broadcast.go:157` (tenant broadcast), `auth/internal/auth/jwt.go:34` (15 min TTL).
- **Suggested fix:** Check `IsWorkspaceMember(node, claims.TenantID)` at WS auth, failing closed, so a reconnect is refused. Also close with an explicit application code the client treats as final. Add a test: removed member reconnects with a still-valid token → auth refused.

## Finding 4: Production reads approval and drive decisions from `policy-read`, which neither the harness nor the cache flush covers
- **Severity:** High
- **Location:** Phase 01 "Harness"; Phase 02 Requirements (L1 flush in `policy/cmd/main.go` only); Phase 04 item 4 ("0 for approval")
- **Flaw:** In prod, approval and drive set `POLICY_READ_SERVICE_ADDR=policy-read:50061`. `policy-read` is a separate binary with its own in-memory graph. It follows the writer through Kafka `graph.mutated` events and shares the L1 Redis cache. The plan (a) puts the L1 flush only in `policy/cmd/main.go`, (b) runs only `policy/cmd` in the harness, so replica lag and the replica's view are never tested, and (c) claims approval exposure is zero, when it is actually bounded by replica lag, or unbounded if the mutation consumer stalls.
- **Failure scenario:** After the 057/058 migrations, deploy restarts both policy services. `policy-read` can repopulate the shared L1 cache from its pre-restart graph after `policy` has flushed, which leaves up to 30 s of stale ALLOW on private-group drives. After a removal, approval `RequireMember` answers from a replica that has not yet consumed the detach events, so a removed approver can still approve during that window. The real-policy tests pass because they talk to the writer.
- **Evidence:** `deploy/docker-compose.prod.yml:463-464` (drive), `:502-503` (approval); `backend/services/policy/cmd/policy-read/main.go:39,58,64,77` (own LoadGraph, shared Redis L1), `:87-99` (Kafka-driven refresher); `backend/services/drive/cmd/main.go:41`.
- **Suggested fix:** Flush L1 in both binaries, or after both have reloaded. State the replica-lag bound in the specs instead of claiming 0. For approval's membership gate, use the writer address (`POLICY_SERVICE_ADDR`), since a read-after-write decision needs it, or add a harness mode that also starts `policy-read`.

## Finding 5: The test policy process connects to the dev Redis and Redpanda, not to "no Redis/Kafka"
- **Severity:** High
- **Location:** Phase 01, Requirements "Harness … no Redis/Kafka (policy only warns)"
- **Flaw:** If `REDIS_URL` and `KAFKA_BROKERS` are not set, policy defaults to `redis://localhost:6379/0` and `localhost:19092`, and so does `realtime.Connect`. Dev infra runs on exactly those ports (docker ps: redis 6379, redpanda 19092), and CI has Redis on 6379. Each harness process will publish graph-mutation and realtime events into the developer's live stack and share its decision cache. With Phase 02, each one will also flush the dev L1 cache on start.
- **Failure scenario:** `make test s=messaging` on a dev box: the test policy publishes `graph.mutated` and permission events. The dev `policy-read` reloads its graph on every test write. The dev messaging consumer sweeps every open call on each `DomainPermission` event (realtime_consumer.go:117-120) and bumps chat counters for test tenants. Running packages in parallel multiplies this. There are two more problems the plan does not address. Each package's test binary builds the policy binary inside the 60 s per-package timeout. And `go-test-strict.sh` counts the planned `t.Skip` (no `TEST_DATABASE_URL`) as a failure.
- **Evidence:** `backend/services/policy/cmd/main.go:39-40,64-79,120`; `backend/pkg/realtime/producer.go:49-55`; `.github/workflows/ci.yml:31-41`; `Makefile:426,436` (`-timeout 60s`); `scripts/go-test-strict.sh:1-15`; `backend/services/messaging/internal/events/realtime_consumer.go:117-120`.
- **Suggested fix:** The harness sets `REDIS_URL=redis://127.0.0.1:1/0` and `KAFKA_BROKERS=127.0.0.1:1` explicitly, or a dedicated Redis DB index. Build the policy binary once in `make test`/CI before the service suites and pass its path in through an env var, so the build cost stays outside each 60 s timeout. Gate real-policy tests on a build tag or an env var instead of `t.Skip`.

## Finding 6: The DM shared-workspace gate covers SendMessage and one StartCall branch, but several other DM write paths stay open
- **Severity:** High
- **Location:** Phase 05, Requirements (calls `:193`, `SendMessage` `messages.go:81-85`) and Success Criteria ("All F4 exploit lines … covered")
- **Flaw:** Writing into a DM takes `write` on its content OA, and that grant lives in the graph, so it survives workspace removal (the DM sits under PC_Global). The plan adds the shared-workspace check in only two places. Every other DM write path still passes on the graph grant alone. The StartCall check at `:193` comes after the early return that hands the caller a ticket into an already-open call.
- **Failure scenario:** An ex-coworker removed from the only shared workspace keeps posting polls and task cards, which send pushes (`polls_tasks.go:105,265`). They can edit old messages (`lifecycle.go:48`), react and pin (`reactions_pins_receipts.go:22,33,71,91`), get a call token or join a ringing call (`calls.go:180-186,247,287,307,539`), ring via `InviteToCall` (`calls_push.go:71`), and upload files to the DM drive (`channel_drive.go:79-82` grants `ChannelDriveOps` incl. upload to the DM members UA, and the drive service checks only the graph).
- **Evidence:** file:line list above; `backend/services/messaging/internal/domain/channels.go:170-188` (DMs under PC_Global).
- **Suggested fix:** Put the gate in one place: `authorizeChannel`, when `ch.ChannelType=="dm"` and the op is not `read`. For the drive, either remove `write/upload` from the departed member's DM edge when the last shared workspace goes, which needs a graph change through EPP, or state the drive as explicitly out of scope. Add deny tests for poll, task, edit, call-join and upload.

## Finding 7: Phase 03 misses a membership caller and leaves ListAccessibleWorkspaces with one lookup per workspace in the system
- **Severity:** Medium
- **Location:** Phase 03, Requirements "Workspace service: replace the PC-ancestor test …"
- **Flaw:** (a) The workspace `ListMembers` still lists every `U` under the PC, so people reachable only through a channel or a role or department UA still show up as workspace members. Phase 03 does not mention it. (b) `ListAccessibleWorkspaces` iterates `store.ListAll()`, which is every workspace on the platform (110 in dev). The plan says to "resolve Members UA ids by name in one pass", but no batch name-lookup RPC exists, so this becomes one `FindNodeByName` per platform workspace on every call. The only mitigation is a cache that Phase 01 marks "optional". (c) `<ws>_Members` is not in the unique node-name index, so parsing ancestor names is not safe without the per-workspace id confirmation.
- **Failure scenario:** (a) After 058, any new path that places a user under the PC (role or department assignment, a future grant) makes them appear in member pickers. The UI then offers to add them, and the new AddMember check denies it. (b) Tenant switcher and boot latency grows linearly with the number of tenants on the platform, and so does the RPC load on policy.
- **Evidence:** `backend/services/workspace/internal/domain/members.go:153-175`; `service.go:258-297`; `backend/proto/policy/policy_read.proto:18-27` (no batch lookup); `data/migrations/025_node_and_drive_root_uniqueness.sql:45-47` (index excludes `_Members`).
- **Suggested fix:** Add `ListMembers` to Phase 03 (descendants of `<W>_Members`). Make the wsID → Members-UA-id cache mandatory, or store `members_ua_id` on `workspaces` (backfilled). Optionally extend the 025 partial unique index to `_Members$` so ancestor names can be parsed safely.

## Finding 8: Phase 04 enforces "active row AND graph" before Phase 07 repairs the rows, and a removal logs the person out of every tenant
- **Severity:** Medium
- **Location:** Phase 04 item 4 (`requireActiveMember` at refresh) vs Phase 07 migration 060 steps 1 and 3; plan.md "Order"
- **Flaw:** Phase 04 makes the row-and-graph conjunction a hard gate at every refresh. The repair for rows (backfilling NULL `ngac_node_id`, inserting a missing row for a graph member) only arrives in Phase 07's 060, possibly several deploys later. The pre-flight query for "graph member without active row" also lives only in Phase 07. Separately, revoking the whole session on a non-member refresh logs out someone removed from org A even though personal workspace P and org B are still valid for them.
- **Failure scenario:** On prod, the personal-workspace owners whose `InsertTenantUser` failed (it is log-only, provisioning.go:44-46) get 401 on every refresh from the Phase 04 deploy until 060 runs. A user removed from one org must sign in again and loses whatever they were doing in B.
- **Evidence:** `backend/services/auth/internal/domain/provisioning.go:44-46`; `refresh.go:201-212`; dev DB: 15 `tenant_users` rows with NULL `ngac_node_id` (138 total).
- **Suggested fix:** Ship 060 step 1 and step 3 (backfill and insert-missing) with 059 in Phase 04, and run its dry-run before the Phase 04 deploy. On a non-member refresh, re-mint for the user's default active tenant (or tenant-less) and send a `tenant_revoked` hint, instead of revoking the session.

Status: DONE_WITH_CONCERNS
Summary: Two load-bearing assumptions break the plan outright. The refresh 503 path spends the token and then the session, so an outage still logs everyone out. Graph-first joinTenant fails for the 83 personal and 8 org workspaces that have no TenantMember UA. Three more claims are false: that closing sockets ends exposure, that the harness is isolated, and that approval exposure is 0 (prod uses policy-read). Phase 05 also misses most DM write paths.
