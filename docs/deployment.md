# Deployment

Production runs at **https://nexus.zaneng.xyz** on one VPS (`160.187.146.173`, Ubuntu 24.04,
Docker + Compose), behind the Traefik that already owns :80/:443 there. Images are built by
GitHub Actions and pulled from a private GHCR; nothing is built on the server.

## The flow

```
push to main -> CI (ci.yml) green -> deploy.yml
   meta      resolve the commit SHA to deploy
   build     10 images (8 services + policy-read + frontend) -> ghcr.io/<owner>/nexus-<name>:<sha> and :main
   deploy    environment "production" waits for a required reviewer, then:
             rsync the release -> /opt/nexus/releases/<sha>/
             ssh: docker login (job token on stdin, private docker config) -> pull
                  -> migrate (pg_dump first) -> up --wait -> restart policy if migrations ran
             health check https://nexus.zaneng.xyz/ and /api/auth/providers
             health fails -> redeploy the previous release from its own files, no migrations
```

Only one deploy runs at a time (`concurrency` group, plus a `flock` on the server).

| File | Role |
|------|------|
| `.github/workflows/deploy.yml` | build, approve, deploy, health check, rollback |
| `deploy/docker-compose.prod.yml` | the stack; installed as `releases/<tag>/docker-compose.yml` |
| `deploy/nginx/` | the edge: SPA plus the `/api/*` reverse proxy (`default.conf`, `proxy.inc`) |
| `deploy/deploy.sh` | server-side: login, pull, migrate, up, record tag (also usable by hand) |
| `deploy/migrate.sh` | migration runner with ledger and backup (compose service `migrate`) |
| `deploy/check-compose-env.sh` | CI check: rendered compose has the env each service needs, no ports |
| `deploy/server-bootstrap.sh` | one-time server preparation |
| `deploy/env.example` | dummy values CI uses to validate the compose file |

Server layout:
```
/opt/nexus/.env  .deployed-tag  .deploy.lock  backups/
/opt/nexus/releases/<tag>/{docker-compose.yml, deploy.sh, migrate.sh, nginx/, db/}   # newest 5 kept
```
Each release carries its own compose file, nginx config and migrations. A rollback runs the
previous release's files, so it never uses a compose file newer than its images.

## Network design: one edge

The Go services speak unauthenticated gRPC to each other, so they must not share a network with
other apps. Compose project `nexus` has an internal network `nexus` (fixed subnet `10.77.231.0/24`)
and joins the shared external network `traefik` with exactly three containers:

- `nexus-frontend`: nginx. Traefik sends every request for `nexus.zaneng.xyz` here. nginx serves the
  SPA and proxies `/api/*` to the services over `nexus`, with the same path rules and precedence as
  the dev Traefik routers (WebSocket first, then document/messaging/asset/drive/approval, then
  auth, then workspace). It has the fixed address `10.77.231.10`.
- `nexus-minio`: only for presigned file URLs on `storage.nexus.zaneng.xyz`.
- `nexus-livekit`: only for the TURN/TLS router on `turn.nexus.zaneng.xyz` (see "Calls (LiveKit)").

- `gotenberg` (Office to PDF for the file viewer) is on its own internal network `previews`, shared only with
  `drive`, and has no route out; see "File previews" below.

Everything else is on `nexus` alone. No container publishes a host port (Docker-published ports
bypass ufw) except `nexus-livekit`: `7881/tcp`, `7882/udp` and the TURN relay range `30000-30049/udp`, exactly, because WebRTC media cannot go
through an HTTP edge. `deploy/check-compose-env.sh` fails if any other service, or LiveKit with other ports, publishes. Names on the shared network are `nexus-` prefixed, and nginx reaches the services by
`nexus-<service>` aliases, so another app cannot shadow them. Same-origin traffic means there is no
CORS middleware.

Client address: Traefik sets `X-Forwarded-For` to the real peer; nginx trusts it only from the
`traefik` network's subnet (`nginx/real-ip.conf`, generated by `deploy.sh` from
`docker network inspect traefik`), then sends the services `X-Forwarded-For`/`X-Real-IP` set to that
client address. The auth service trusts those headers from `10.77.231.10/32` only
(`AUTH_TRUSTED_PROXIES`), which keeps per-address rate limits meaningful.

The shared Traefik redirects `web` -> `websecure` globally (an entryPoint redirection in its
`traefik.yml`), so the labels here only define the `websecure` routers (cert resolver `le`); no
per-app http redirect is needed. Router names are `nexus-*` because Traefik's names are global.

Routes the frontend uses, all covered: `/api/auth`, `/api/me[/...]`, `/api/workspaces/...`
(including `documents`, `channels`, `asset*`, `drive`, `contacts` sub-paths), `/api/invitations`,
`/api/documents`, `/api/channels`, `/api/messages`, `/api/dms`, `/api/threads`,
`/api/notifications`, `/api/polls`, `/api/tasks`, `/api/calls`, `/api/assets`, `/api/asset-types`,
`/api/asset-requests`, `/api/drive`, `/api/approval`, `/api/ws`, and `/livekit/` (call signalling, WebSocket,
to `nexus-livekit:7880` with the prefix stripped). Not routed publicly, on purpose
(also unrouted in dev Traefik): `/api/admin` (tenant provisioning in the approval service) and
`/internal/livekit/webhook` (LiveKit reaches messaging over the `nexus` network). Any
other `/api/...` returns a JSON 404.

## Calls (LiveKit)

Voice and video calls run on a self-hosted `livekit-server` (`nexus-livekit`, image pinned in
`deploy/docker-compose.prod.yml`; dev: `livekit` in `docker-compose.yml`, config
`deploy/livekit/livekit.dev.yaml`). The messaging service signs call tokens and receives LiveKit's
webhooks; browsers talk to LiveKit directly.

```
browser --wss://nexus.zaneng.xyz/livekit/--> Traefik --> nginx (/livekit/) --> nexus-livekit:7880   signalling
browser --UDP 7882 / TCP 7881 (host ports)----------------------------------> nexus-livekit        media
browser --TLS turn.nexus.zaneng.xyz:443--> Traefik (TCP router, SNI) --> nexus-livekit:443          TURN/TLS, UDP-blocked networks
nexus-livekit --http://nexus-messaging:8080/internal/livekit/webhook--> messaging                    room events
```

**Port exception.** `nexus-livekit` is the only container that publishes host ports: `7881/tcp` (ICE-TCP
fallback), `7882/udp` (all media on one UDP port, instead of a 50000-60000 range) and `30000-30049/udp`
(TURN relay ports, `turn.relay_range_*`: a client behind TURN is reached at the public IP plus one of these, one
port per relayed client, so 50 at once); the check script allows nothing else. Docker-published ports bypass ufw: they are reachable as soon as the container runs,
whatever ufw says, so there is no ufw step — a host firewall in front (the provider's) must let them
through. LiveKit is also on the shared `traefik` network for the TURN router, so its API (7880, every call
needs a key-signed token) is reachable from other containers there; that is the accepted cost of TURN/TLS.
Media binds only the `nexus` address (`rtc.ips.includes: [10.77.231.0/24]`): Docker forwards the published ports
there, and answering from the `traefik` address sent replies out by another route, so no call from the Internet
connected. Rooms are opened only by messaging (`room.auto_create: false`), and TURN listens on TLS only (`udp_port: 0`).
`use_external_ip` makes LiveKit discover the VPS address through STUN; if it picks the wrong one behind
NAT, set `rtc.node_ip: 160.187.146.173` in the inline config.

**One-time steps (done by hand; `server-bootstrap.sh` does not touch firewalls or Traefik):**

1. If the provider has a firewall in front of the VPS, open `7881/tcp`, `7882/udp` and `30000-30049/udp` there.
2. DNS: A record `turn.nexus.zaneng.xyz` -> `160.187.146.173`.
3. The shared Traefik must have TCP routers enabled on its `websecure` entryPoint (it does by default
   with the docker provider). Without the TURN router, calls still work except on networks that block
   UDP and everything but 443.
4. Re-run `deploy/server-bootstrap.sh` (it appends a generated `LIVEKIT_API_KEY`/`LIVEKIT_API_SECRET` when absent; the deploy fails until both exist), or generate them by hand:
   `docker run --rm livekit/livekit-server:v1.13.7 generate-keys` ->
   `LIVEKIT_API_KEY=<API Key>` and `LIVEKIT_API_SECRET=<API Secret>` (secret >= 32 characters).

**Environment.** `nexus-livekit` takes the key pair as `LIVEKIT_KEYS`. `messaging` gets
`LIVEKIT_URL=http://nexus-livekit:7880` (server API), `LIVEKIT_PUBLIC_URL=wss://nexus.zaneng.xyz/livekit`
(what browsers connect to), `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET`. Dev values are in `.env.example`
(`ws://localhost:5173/livekit` through the Vite `/livekit` proxy).

**Check.** `curl https://nexus.zaneng.xyz/livekit/` answers `200 OK`. TURN/TLS:
`openssl s_client -connect turn.nexus.zaneng.xyz:443 -servername turn.nexus.zaneng.xyz` presents the
Let's Encrypt certificate. Media: a call between two networks, one with UDP blocked, shows a `relay`
candidate in `chrome://webrtc-internals`.

**LiveKit Cloud instead.** Set `LIVEKIT_URL` to the project's `https://<project>.livekit.cloud`,
`LIVEKIT_PUBLIC_URL` to its `wss://` address and the key pair to the project's; remove `nexus-livekit`,
the `/livekit/` nginx location and the Traefik TURN router, and point the cloud project's webhook at a
public messaging endpoint (the webhook is not routed publicly here).

## One-time setup

1. **DNS.** A records `nexus.zaneng.xyz` and `storage.nexus.zaneng.xyz` -> `160.187.146.173`
   (the second is MinIO's S3 endpoint for presigned URLs).
2. **Deploy key.** On your machine:
   ```bash
   ssh-keygen -t ed25519 -N '' -C nexus-deploy -f ./nexus-deploy
   ```
   `nexus-deploy` (private) becomes the secret `DEPLOY_SSH_KEY`; `nexus-deploy.pub` goes to the
   bootstrap. The key is root-equivalent on the VPS; use it for this workflow only.
3. **Host key, pinned.** `DEPLOY_KNOWN_HOSTS` holds the server's SSH host key. The fingerprint
   was checked over an already-trusted SSH session to the server (the one the operator already
   uses), by comparing the output of `ssh-keyscan -t ed25519 160.187.146.173 | ssh-keygen -lf -`
   with `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` run on the server. Without such a
   session, read the fingerprint from the provider's web console / VNC console on the server
   instead, never from the same unauthenticated network path you are verifying.
   ```bash
   ssh-keyscan -t ed25519 160.187.146.173 > known_hosts.txt
   ```
   The file's content is the secret `DEPLOY_KNOWN_HOSTS`.
4. **GitHub.** Both secrets are **environment** secrets of the `production` environment (not
   repository secrets), so only jobs that passed the approval can read them:
   - Settings -> Environments -> `production` -> Environment secrets: `DEPLOY_SSH_KEY`,
     `DEPLOY_KNOWN_HOSTS`.
   - Required reviewers: the repository owner is the only reviewer. "Prevent self-review" only
     matters with more than one reviewer; with a single reviewer who is also the pusher, leave it
     off or nobody could approve.
   - Deployment branches and tags: **Selected branches** -> `main`.
   (`GITHUB_TOKEN` needs nothing extra; the workflow sets its own permissions.)
5. **Bootstrap the server** (copy `deploy/server-bootstrap.sh` over, run as root):
   ```bash
   scp deploy/server-bootstrap.sh nexus-deploy.pub root@160.187.146.173:/root/
   ssh root@160.187.146.173 'bash /root/server-bootstrap.sh --pubkey-file /root/nexus-deploy.pub'
   ```
   It creates `/opt/nexus` with `backups/` and `releases/`, writes `/opt/nexus/.env` (mode 600) with
   generated secrets, checks the `traefik` network exists, and appends the key to
   `/root/.ssh/authorized_keys` as `restrict ssh-ed25519 ...` (`restrict` only drops pty and
   forwarding, which rsync and plain ssh commands do not use). Re-running is safe: existing
   values are never rewritten.
6. **Fill the placeholders** in `/opt/nexus/.env`:
   - `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`: a "Web application" OAuth client in Google
     Cloud Console, with `https://nexus.zaneng.xyz/api/auth/google/callback` under Authorized
     redirect URIs. Without them, Google sign-in is off.
   - Email sign-in codes: the Gmail SMTP block below. Without it (and without Google) nobody can
     log in, because the fixed OTP test code is disabled in the compose file.
   - `SMTP_*`: see [Email sign-in codes (Gmail SMTP)](#email-sign-in-codes-gmail-smtp).
7. **Package access.** After the first image push, if the deploy job cannot pull, open each
   `nexus-*` package -> Package settings -> Manage Actions access and give this repository read
   access (the images carry the `org.opencontainers.image.source` label that normally links them).

### Adding `INTERNAL_IDENTITY_SECRET` to a server bootstrapped earlier

Services sign the identity they send each other over gRPC with `INTERNAL_IDENTITY_SECRET`
(see `docs/specs/resource-pep-coverage/spec.md`). `docker-compose.prod.yml` requires it, so a
deploy to a server whose `/opt/nexus/.env` lacks it stops at `docker compose` before any
container is touched. Add it once, **before** the first deploy that contains this change, by
re-running the bootstrap, which appends missing keys only and never rewrites an existing one:

```bash
scp deploy/server-bootstrap.sh root@160.187.146.173:/root/
ssh root@160.187.146.173 'bash /root/server-bootstrap.sh'
ssh root@160.187.146.173 "grep -c '^INTERNAL_IDENTITY_SECRET=.' /opt/nexus/.env"   # prints 1
```

The bootstrap output lists `added keys: INTERNAL_IDENTITY_SECRET` and never prints the value.

To rotate it, three deploys, because a deploy replaces containers one at a time and a recreated
container that signs with a secret its not-yet-restarted peers cannot verify is refused. Let OLD
be the value now in `/opt/nexus/.env` and NEW a fresh `openssl rand -hex 48`:

1. `INTERNAL_IDENTITY_SECRET=OLD`, `INTERNAL_IDENTITY_SECRET_PREVIOUS=NEW`, deploy (everything signs
   OLD and accepts both).
2. `INTERNAL_IDENTITY_SECRET=NEW`, `INTERNAL_IDENTITY_SECRET_PREVIOUS=OLD`, deploy (everything signs
   NEW and still accepts OLD).
3. Delete `INTERNAL_IDENTITY_SECRET_PREVIOUS`, deploy.

After a suspected leak do not keep the leaked value as `_PREVIOUS`: set only the new secret in one
deploy and accept a short burst of `Unauthenticated` while containers are replaced.

## Deploying

Merge to `main`. When CI is green, `Deploy` builds the images, then pauses at `production`;
approve it in the run page. The run summary shows the health check.

**Redeploy / rollback** (Actions -> Deploy -> Run workflow, branch `main`):
- empty tag: build and deploy the current `main` again;
- `tag` = an earlier commit SHA: deploy those images without rebuilding, using that release's own
  files if `/opt/nexus/releases/<tag>/` still exists. It still waits for approval and, like every
  redeploy, runs the migrations that release ships (a no-op when already applied).

An automatic rollback (health check failed) and `ROLLBACK=1` runs skip migrations entirely.
Migrations are forward-only: rolling back the images does not undo schema changes, so make
migrations backward compatible with the previous release.

## Working on the server

```bash
cd /opt/nexus/releases/$(cat /opt/nexus/.deployed-tag)
export COMPOSE_ENV_FILES=/opt/nexus/.env NEXUS_HOME=/opt/nexus NEXUS_OWNER=<owner> NEXUS_TAG=$(cat /opt/nexus/.deployed-tag)
docker compose ps
docker compose logs -f --tail 200 auth          # any service; JSON logs, rotated 3 x 10 MB
```
Deploy by hand (registry login only needed when the images are not already local):
```bash
cd /opt/nexus/releases/<sha>
printf '%s' "$GH_PAT_READ_PACKAGES" | NEXUS_OWNER=<owner> GHCR_USER=<user> ./deploy.sh <sha>
SKIP_PULL=1 NEXUS_OWNER=<owner> ./deploy.sh <sha> </dev/null    # images already local
ROLLBACK=1 NEXUS_OWNER=<owner> ./deploy.sh <sha> </dev/null     # no migrations, tolerant pull
cat /opt/nexus/.deployed-tag                                      # last tag that came up healthy
```
`deploy.sh` logs in to ghcr.io inside a private, temporary docker config and deletes it on exit;
root's own docker credentials (and other apps' logins) are never read or removed.

Deploy and migration output (the one-off `migrate` container is removed after it runs) is in the
GitHub Actions run. TLS and routing: the Traefik logs under `/opt/traefik`.

## If the first deploy fails

The first run has no previous release, so there is nothing to roll back to; the stack is left as it
came up. Work through:

1. **Which step failed?** Open the Actions run: SSH/rsync (key, known_hosts, `restrict`), pull
   (package access), migrate (output of `migrate.sh`), `up --wait` (a container never became
   healthy), or Health check (public URL).
2. **Logs on the server:** `cd /opt/nexus/releases/<sha>`, export the variables from
   [Working on the server](#working-on-the-server), then `docker compose ps` and
   `docker compose logs --tail 100 <service>` for the unhealthy one. `postgres` and `policy` first:
   everything else waits for them.
3. **Reset without losing data:** `docker compose down` (**never** `-v`: that deletes the database
   and MinIO volumes), fix the cause, then re-run the workflow (Run workflow, empty tag) or
   `./deploy.sh <sha>`. Migrations already applied are in the ledger and are skipped.
4. **DNS:** `dig +short nexus.zaneng.xyz storage.nexus.zaneng.xyz` must both print
   `160.187.146.173`.
5. **Let's Encrypt:** the certificate is requested on the first https request after Traefik sees the
   router. Check `docker logs` of the Traefik container for `nexus.zaneng.xyz` (ACME errors:
   DNS not yet pointing at the server, port 80 blocked, rate limits). Until it is issued the health
   check fails with a TLS error and `curl -k` works.
6. **Package access:** `denied` / `unauthorized` on pull -> each `nexus-*` package needs read access
   for this repository (setup step 7). A freshly pushed package is private to its publisher.
7. **Registry or `.env` problems:** `docker compose config` from the release directory prints the
   resolved file and names any variable missing from `/opt/nexus/.env`.

## Migrations

`migrate.sh` runs before every `up` (except on rollback). It keeps a ledger table
`schema_migrations(filename, checksum, applied_at)`.
- Fresh database: applies `data/init.sql` (ledger name `init.sql`), then every
  `data/migrations/*.sql` in sorted order.
- Later: applies only files not in the ledger. A recorded file whose checksum changed aborts the
  run (exit 3) before anything is touched: add a new migration instead of editing an old one.
- Each file runs in one transaction together with its ledger row. Files that manage their own
  `BEGIN/COMMIT`, use `CREATE [UNIQUE] INDEX CONCURRENTLY` / `ALTER TYPE ... ADD VALUE` /
  `VACUUM` / `CREATE DATABASE`, or contain the line `-- migrate:no-transaction` run as written and
  get their ledger row afterwards. **Such files must be idempotent**: if the run dies between the
  file and its ledger row, the next deploy runs the file again.
- When anything was applied, `deploy.sh` restarts `policy` and `policy-read` after `up`, because
  they hold the authorization graph in memory and read the database only at start.
- **`051_message_search_simple.sql` rewrites the `messages` table.** A generated column cannot change its
  expression in place, so the migration drops `search_vector`, adds it back (every row recomputed) and rebuilds the
  GIN index; the `ALTER TABLE` takes an ACCESS EXCLUSIVE lock, so `messages` blocks reads and writes (every message
  list, send and search waits) for the whole rewrite and index build, which grows with the table (401 rows in dev take
  milliseconds). Deploy it outside busy hours. The pre-migration dump is the rollback of record; the SQL
  to return to the English configuration is in the migration header.
- `050_messages_latest_per_channel.sql` builds its two indexes with `CREATE INDEX CONCURRENTLY IF NOT EXISTS`, so
  writes to `messages` continue during the build. It therefore runs outside a transaction (see above) and is
  idempotent; an interrupted build leaves an INVALID index of the same name, which must be dropped before the file is
  applied again.
- The migration files travel with each release into `releases/<tag>/db/` (not baked into an
  image), so they always match the commit being deployed and need no extra image.

## Backups and restore

Before any migration that has something to apply (and only on a non-empty database), `migrate.sh`
writes `/opt/nexus/backups/nexus-<UTC timestamp>.dump` (`pg_dump -Fc`) and keeps the newest 14.
A failed dump stops the deploy. Backups of MinIO objects are not made.

Restore (stops the apps, replaces the database content):
```bash
cd /opt/nexus/releases/$(cat /opt/nexus/.deployed-tag)
export COMPOSE_ENV_FILES=/opt/nexus/.env NEXUS_HOME=/opt/nexus NEXUS_OWNER=<owner> NEXUS_TAG=$(cat /opt/nexus/.deployed-tag)
# 1. Safety dump of what is there now, in case the restore is the wrong move.
docker compose exec -T postgres pg_dump -U ngac -Fc ngac > /opt/nexus/backups/pre-restore-$(date -u +%Y%m%dT%H%M%SZ).dump
# 2. Stop everything that talks to the database.
docker compose stop auth workspace document messaging asset drive approval policy policy-read nexus-frontend
# 3. Replace the database.
docker compose exec -T postgres dropdb   -U ngac ngac
docker compose exec -T postgres createdb -U ngac ngac
docker compose exec -T postgres pg_restore -U ngac -d ngac --no-owner < /opt/nexus/backups/nexus-<stamp>.dump
# 4. Flush Redis: sessions, flows and caches refer to rows that may no longer exist.
docker compose exec -T redis sh -c 'redis-cli FLUSHALL'
# 5. Start again (policy reloads the graph from the restored data).
docker compose up -d --wait
```
If the restored database predates some migrations, the ledger in the dump matches it and the next
deploy re-applies the rest. Users are signed out by the Redis flush.

## MinIO image

MinIO no longer publishes images on Docker Hub (`minio/minio`) or Quay. Production runs the
official `minio/minio:RELEASE.2025-09-07T16-13-09Z` image (the release dev uses), mirrored
unchanged to the private `ghcr.io/<owner>/nexus-minio` package. To refresh the mirror from a
machine that still has the image: `docker tag minio/minio:<release> ghcr.io/<owner>/nexus-minio:<release>`
then `docker push` (needs a token with `write:packages`). Set `MINIO_IMAGE` in `/opt/nexus/.env`
to use another image instead. Replacing the
image later is safe: the data lives in the `miniodata` volume.

## Resources and limits

Memory limits total about 3.6 GB for the whole stack (postgres 512M, redpanda 640M, redis 256M,
minio 256M, gotenberg 600M (1 CPU), policy 256M, policy-read 192M, the rest 128-160M, nginx 48M). Go services also get
`GOMEMLIMIT` just under their limit. `policy-read` runs one replica (dev runs two).

## File previews (Gotenberg)

Opening a Word, PowerPoint, OpenDocument text/presentation or RTF file (doc, docx, ppt, pptx, odt, odp, rtf) in the
viewer makes the drive service send it to `gotenberg` (image `gotenberg/gotenberg:8.37.0`, LibreOffice inside,
from Docker Hub), which answers a PDF; the PDF is kept in MinIO under `drive/previews/` and reused. Spreadsheets
(xls, xlsx, ods) are not converted: the viewer reads them as tables. A file is converted on the machine that runs
the stack, by a container with no route out; it is not sent to any outside service.

`gotenberg` is limited to 600M, 1 CPU and 300 processes, and runs only its LibreOffice route (Chromium, PDF-engine,
webhook and download-from features are switched off; LibreOffice may not fetch from private addresses). It sits on
the `previews` network (`internal: true`, no route out, no published port) with `drive` as its only peer; `drive`
finds it through `GOTENBERG_URL=http://gotenberg:3000`. Optional tuning on `drive`: `PREVIEW_MAX_SOURCE_MB` (50),
`PREVIEW_MAX_PDF_MB` (80), `PREVIEW_MAX_CONCURRENT` (2), `PREVIEW_CONVERT_TIMEOUT_SECONDS` (45, under nginx's 60 s
read timeout) and `PREVIEW_FAILURE_TTL_MINUTES` (10, how long a file that failed is not retried). The PDF is
spooled to a temporary file in the drive container, never held in memory.

`drive` fetches the original and stores the PDF through the signed MinIO URLs that browsers use. Those name the
public host (`storage.nexus.zaneng.xyz`, part of the signature), which from inside the stack would mean going out
through the shared Traefik and back. Instead `PREVIEW_STORAGE_DIAL_ADDR=nexus-minio:9000` makes `drive` connect to
MinIO directly on the `nexus` network, in plain http, still sending the public host as `Host`, so the signature
holds. Unset (dev), URLs are used as they are.

If Gotenberg is down or a document cannot be converted, previews answer "unavailable" (the viewer offers the
download) and the drive logs a warning; nothing else is affected. A permanently deleted file takes its PDF with it.
Dev: `docker compose up -d gotenberg` (also part of `make dev-infra`) publishes it on `127.0.0.1:3050`, which a
native drive uses by default.

Checks after a deploy that includes previews (the drive image has `wget`):

```bash
docker exec nexus-drive-1 wget -qO- http://nexus-minio:9000/minio/health/live && echo minio-ok   # drive reaches MinIO directly
docker exec nexus-drive-1 wget -qO- http://gotenberg:3000/health                                  # and the converter
```

## Web push (OneSignal)

The messaging service sends web push notifications through OneSignal's REST API for direct messages,
mentions and replies in threads a person follows. It needs two values in `/opt/nexus/.env`:

- `ONESIGNAL_APP_ID` — the app's id, from the OneSignal dashboard (public; the frontend uses the same value
  as `VITE_ONESIGNAL_APP_ID`).
- `ONESIGNAL_REST_API_KEY` — the app's REST API key (secret; never in git, never in the frontend).

For the frontend, `VITE_ONESIGNAL_APP_ID` is baked into the SPA bundle at build time via Docker build arg
(`ARG VITE_ONESIGNAL_APP_ID` in `frontend/Dockerfile`). In `.github/workflows/deploy.yml`, it is read from
the repository variable `vars.VITE_ONESIGNAL_APP_ID` (Settings → Secrets and variables → Actions → Variables;
it is public, never stored as a secret). When absent or empty, the SDK is not loaded and push UI remains hidden.

Both empty: push is off and nothing is sent. Only one set: messaging refuses to start, so a half-configured
deployment never silently sends nothing. Devices are linked to people by OneSignal's `external_id`, set to the
user's id at sign-in. Each recipient is checked for `read` on the channel when the push is sent.

A notification opens `APP_BASE_URL` plus the conversation's path (web push needs an absolute address), and
replaces an earlier one about the same conversation through `web_push_topic`. Each request carries an
`idempotency_key`, so a retry after a timeout does not deliver twice. A conversation is not pushed to a
person while one of their sessions has it on screen with the page visible; a tab that is merely open, or
subscribed to the conversation for the navigator, does not hold push back.

## Installable app (PWA)

The frontend build contains `sw.js` (the service worker), `manifest.webmanifest` and the icons. nginx serves
`/sw.js` and `/manifest.webmanifest` with `Cache-Control: no-cache` (`deploy/nginx/default.conf`), so an installed
app learns of a new release on its next open. Every other static file (`.js .css .png .svg .woff2 …`) is cached for 30
days as immutable: the hashed files under `assets/` are safe, but the fixed-name icons (`/icon-*.png`, `/favicon.svg`,
`/apple-touch-icon.png`) are too, so a changed icon reaches home-screen installs only after that time (rename it to
force one).
The worker lives at the site root, so its scope is already `/` and no `Service-Worker-Allowed` header is needed.
Traefik adds nothing here and does not cache. Browsers install only over HTTPS (the production host is). The worker
precaches the app shell and never `/api/*`; a release shows installed apps a "Có bản mới của Nexus" bar.
With push configured, OneSignal registers the worker as `/OneSignalSDKWorker.js` (the name on its dashboard wins over
`serviceWorkerPath` in code). That file only imports `/sw.js` and is served `no-cache` too; without it the
registration 404s and no device can turn push on.

## Email sign-in codes (Gmail SMTP)

The auth service sends one-time sign-in codes by email through SMTP (Go standard library, no
extra dependency). When `SMTP_HOST` is set, `/api/auth/providers` reports `otp_proves_email: true`
and a code typed correctly also marks the address verified. The fixed test code stays off.

The same `SMTP_*` values and `APP_BASE_URL` also serve the workspace service, which emails an
invitation to the invited address ("<inviter> mời bạn vào <workspace> trên Nexus", with a link to
`APP_BASE_URL`). There is nothing else to configure: one Gmail account sends both. Without
`SMTP_HOST`, invitations are still recorded and nothing is emailed.

1. Turn on **2-Step Verification** for the Gmail account.
2. Create an **App Password** at https://myaccount.google.com/apppasswords (any name, e.g.
   "Nexus"). Google shows 16 characters, in groups of four; remove the spaces.
3. Set these in `/opt/nexus/.env` on the server (append the lines; `server-bootstrap.sh` does not
   create them):
   ```
   SMTP_HOST=smtp.gmail.com
   SMTP_PORT=587
   SMTP_USERNAME=you@gmail.com
   SMTP_PASSWORD=<the 16-character app password>
   SMTP_FROM=Nexus <you@gmail.com>
   ```
   `SMTP_USERNAME` is the full Gmail address. Port 587 uses STARTTLS; for port 465 (implicit TLS)
   set `SMTP_PORT=465`. `SMTP_TLS` (`starttls` or `tls`) is optional and defaults by port. There
   is no plaintext mode, and a server that does not offer STARTTLS is refused.
4. Limits: a personal Gmail account may send about 500 messages a day. `SMTP_FROM` must be the
   Gmail account itself or an alias verified in Gmail ("Send mail as"); Gmail rewrites any other
   From address.
5. Put the values **only** in `/opt/nexus/.env` on the server (mode 600). Never in the repository,
   in `deploy/env.example`, or in GitHub secrets. A literal `$` in the password must be written
   `$$`. Then apply with `docker compose up -d auth workspace` from the current release directory (see
[Working on the server](#working-on-the-server)).

If `SMTP_HOST` is set but the rest is incomplete, the auth service refuses to start and says
which part is wrong (never echoing the password). A failed send returns a generic 500 to the
caller, with the cause only in the auth log, and leaves no usable session; the response does not
depend on whether the address has an account. The code itself is never logged.

The workspace service refuses to start on the same half-configured `SMTP_*`, and on an
`APP_BASE_URL` that is not an absolute http(s) URL. An invitation email is sent in the
background after the invitation is stored: the invite request answers 202 at the same speed
whether or not the mail goes out, and a failure is only a warning in the workspace log, with the
address masked and the body never logged. Inviting the same pending address again within 10
minutes of the last email sends nothing new (the `last_emailed_at` column of
`workspace_invitations`, migration 036).

## Presigned file URLs

The document service signs upload and download URLs for the public storage host so browsers on
the https site get `https://storage.nexus.zaneng.xyz/...` links. Two clients are involved: the
internal one (`MINIO_ENDPOINT=nexus-minio:9000`, plain, for server-side work) and a signing-only client
for `MINIO_PUBLIC_ENDPOINT=storage.nexus.zaneng.xyz` with `MINIO_PUBLIC_SECURE=true` (both set in
the compose file; unset, dev keeps plain http). The signature covers the Host header, so the
`nexus-storage` Traefik router (host `storage.nexus.zaneng.xyz`, MinIO API port 9000, never the
console) must forward the host unchanged, which it does by default. DNS for
`storage.nexus.zaneng.xyz` is required, as listed above.
